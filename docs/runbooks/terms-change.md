# Runbook: changing the Terms of Service or Privacy Policy

Since Sprint 259a every new account agrees to a specific version of each document, and the app records it
(`public.legal_acceptances`). This runbook keeps those records true. Claude runs it; the owner approves the text.

## 1. Words
- **Revision date** = the version label (`YYYY-MM-DD`), the day the text was finalized. Shown as "Last updated".
- **Effective date** = the first production deploy that serves the text. Record it in the handoff with the commit.
- **Cutoff** (`AGREEMENT_REQUIRED_FROM`) = accounts created at or after it must agree before using the app.
  Older accounts are not asked until a version change says so (step 4).

## 2. Is it a change "that matters"?
Our Terms promise: "If we change these terms in a way that matters, we will tell you in the app or by email before
the change takes effect." Anything that changes rights, duties, money, liability, disputes, data use or who the
company is matters. Typos and formatting don't, but any change to the text still needs a new version (step 3).

## 3. Publish a new version (never edit a published one)
1. Edit `components/legal/terms-document.tsx` or `privacy-document.tsx`.
2. Add a new archive file `apps/web/legal-archive/<doc>/<YYYY-MM-DD>.txt` (generated by `legalDocumentText`) and a new
   registry entry in `lib/legal-versions.ts`; move `current` to it. Never change an older file or its hash: rows point
   at them, and the tests fail if they change.
3. `npm run gate:web` must pass (V1–V3 prove the page, sheet, archive and hash match).
4. ChatGPT review for any change that matters (L3).

## 4. Asking people again
- A new version makes every account that agreed to an older version see "We updated our Terms" once.
- **Before a change that matters takes effect:** give notice first (in-app banner or email; emails need the owner's
  go while notifications are off), wait the notice period stated in the Terms, then ship the version. Don't bump a
  version while an App Store build is in review.
- **Older accounts (created before the cutoff)** are asked only by a sprint that turns them on, with the same notice.
- **Tenants who don't agree** must keep: receipts, rent history, the lease, data export, account deletion, sign out,
  a way to stop autopay, and the landlord's contact. Check `/agree`'s "Don't want to agree?" block before shipping.

## 5. After the deploy
- Archive actual-size screenshots (web and iPhone, light and dark, empty / error / checked states) under
  `docs/legal/consent-screens/<version>/` with the commit in the file name.
- Update the rules map row "Contract formation" and the handoff (version, effective date, commit).

## 6. The email key for agreement records
- `LEGAL_RECORD_HMAC_KEY` (Vercel, production and preview; `apps/web/.env.local`) turns each person's email into
  `legal_acceptances.email_hmac`, so a record still shows who agreed after their account is anonymized.
- **Backup:** the owner keeps a copy in their password manager. Without the key, old hashes can't be checked.
- **Rotation:** make a new key, bump `LEGAL_RECORD_HMAC_KEY_VERSION` in `lib/legal-acceptance.ts`, deploy; new rows
  carry the new `email_hmac_key_version`. Keep every old key (labeled with its version) for as long as rows using it
  are kept (10 years after the account closes).
- **If the key leaks:** rotate as above; old hashes stay valid for proof, but treat them as linkable to emails.
- **Check after any deploy that touches it:** the release E2E writes a record (`check` shows it); a missing key shows
  as `[legal] acceptance not saved` with code `no_hmac_key` in Vercel logs.
